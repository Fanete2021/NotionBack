# Правила организации кода

## 1. Размер файла

Один файл не больше **150 строк**, край — **200 строк**.

## 2. Структура папок

- Типы → `types/`
- Константы → `constants/`
- Утилиты → `utils/`

Всё по месту. В типах только типы, в константах только константы, в утилитах только утилиты. Несколько констант и утилит ещё можно хранить в одном файле — их размер это позволяет, утилиты следует делить по одной функции на файл, даже если утилита 5 строк кода.

## 3. Barrel файлы

Barrel файлы для удобного и красивого импорта. В каждой папке, файлы которой хоть где-то используются, добавить `index.ts` и реэкспорт.

### Для чего это надо:

Чтобы импорты не выглядели так:

```typescript
import { S3CleanupService } from '../../s3/services/s3-cleanup.service';
import { S3UrlService } from '../../s3/services/s3-url.service';
import { S3ObjectService } from '../../s3/services/s3-object.service';
```

А так:

```typescript
import {
  S3CleanupService,
  S3UrlService,
  S3ObjectService,
} from '../../s3/services';
```

## 4. Алиасы

Относительные пути вида `../../../` затрудняют чтение и легко ломаются при переносе файла между папками. Вместо этого настраиваются алиасы — короткие абсолютные пути от корня `src`.

### Настройка

В `tsconfig.json`:

```json
{
  "compilerOptions": {
    "baseUrl": ".",
    "paths": {
      "@app/*": ["src/app/*"],
      "@common/*": ["src/common/*"],
      "@modules/*": ["src/modules/*"],
      "@s3/*": ["src/s3/*"]
    }
  }
}
```

### Как использовать

Вместо:

```typescript
import { S3ObjectService } from '../../../s3/services';
```

Пишем:

```typescript
import { S3ObjectService } from '@s3/services';
```

### Для чего это надо:

- Путь не зависит от того, где лежит файл, который импортирует — при переносе файла импорты не ломаются.
- Сразу видно, из какого модуля пришла зависимость (`@s3`, `@common`, `@modules`), а не приходится считать `../..`.
- Меньше визуального шума в начале файла.

### Правило

Один алиас — один корневой домен (`common`, `modules`, `s3` и т.д.), без глубокой вложенности вроде `@modules/s3/services/impl/*`. Если хочется завести алиас на подпапку — это сигнал, что подпапке пора становиться отдельным модулем (см. п. 7).

## 5. Экспорт внизу файла

Экспорт констант, утилит, типов делать внизу, следующим образом:

```typescript
interface User {}

export type { User };
```

### Для чего это надо:

- Когда открываешь файл, сразу внизу видно всё публичное API — не нужно прокручивать весь файл в поисках экспортов.
- Выглядит лаконичнее, не нужно обращать внимание на `export`, если надо быстро отредактировать тип.

## 6. Репозиторий — одна модель

Репозиторий нацелен на одну модель: `WorkspaceRepository` обслуживает только модель `Workspace`, не `WorkspaceMembers`.

### Для чего это надо:

Декомпозиция. Чем больше моделей обслуживает репозиторий — тем больше код, тем сложнее читать.

## 7. Подмодули для дочерних моделей

Пункт вытекает из предыдущего. Для работы с дочерними моделями стоит рассмотреть подмодуль с отдельной инфраструктурой:

- модуль
- сервис
- репозиторий
- и, возможно, контроллер

## 8. Правило двух использований

Если утилита используется в двух и более местах — только в таком случае эта утилита является shared/common. Преждевременной оптимизацией заниматься себе дороже.

### Пример:

`HttpExceptionsFilter`, как и `PrismaExceptionFilter`, используется только в одном месте — в `main.ts`. Им нет места в `Common`, пока они не будут использоваться дважды — как только так сразу полетит в shared.

На данный момент стоит создать рядом с `main.ts` папку `filters` и закинуть их туда.

---

Самое самое главное — продуктивность повышается от декомпозиции. Код не должен читаться как что-то сложное, даже если там код по запуску ядерной ракеты. Это позволяет не только писать более самодокументируемый код, но и качественный, ведь в утилите на 13 строчек тяжело дать осечку, а в утилите на 200 — очень легко.
