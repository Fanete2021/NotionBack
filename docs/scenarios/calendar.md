# Календарь: события (BE-5.3)

Модуль отвечает за **события календаря** (`CalendarEvent`) — сущности воркспейса, опционально привязанные к проекту.

На панели дня фронта событие показывается как задача с чекбоксом. Статус чекбокса — поле `isCompleted` у `CalendarEvent`. Отдельный todo-список со сроком `dueAt` (без диапазона начала и конца) по-прежнему не этот модуль.

## Доступ и авторизация

- Все эндпоинты требуют JWT (глобальный `JwtAuthGuard`).
- **Список и создание** — под воркспейсом (`/api/workspaces/:workspaceId/events`), членство проверяет `WorkspaceMemberGuard` (`assertMemberOf`).
- **Обновление и удаление** — по id (`PATCH` / `DELETE /api/events/:id`). **Отметка выполнения** — `PATCH /api/events/:id/completion`. Отдельный `WorkspaceEventGuard` загружает событие, берёт его `workspaceId` и проверяет членство. Событие кладётся в `request`, чтобы сервис не читал его из БД повторно.
- Любой член воркспейса может редактировать, отмечать выполненным и удалять любое событие в нём (как у проектов; отдельной проверки авторства нет).

## Ограничения целостности на уровне БД

- У проекта есть `@@unique([id, workspaceId])`, а событие ссылается на проект **композитным ключом** `(projectId, workspaceId) → (id, workspaceId)`. То есть БД сама гарантирует, что проект принадлежит **тому же воркспейсу** — проверку в коде (`assertProjectInWorkspace`, 400) не обойти.
- `projectId` опционален (`NULL`) — событие может быть без проекта. При `NULL` композитный FK не проверяется (MATCH SIMPLE в Postgres).
- `onDelete: Cascade`: при удалении воркспейса или проекта связанные события удаляются автоматически.
- Нарушения FK/unique превращаются в понятные ответы глобальным `PrismaExceptionFilter`: P2002→409, P2003→400, P2025→404.

## Поля события

`title`, `startAt`, `endAt`, `allDay`, `isCompleted`, `projectId?`. **Без recurrence** (повторение) — по ТЗ.

`isCompleted` по умолчанию `false`. Через общий `PATCH` его не меняют — только отдельной ручкой отметки выполнения.

> Напоминания (чекбокс «Напомнить мне» / «Отправить в Telegram» на макете) в модель события **не входят** — это отдельная фича интеграции с ТГ-ботом (BullMQ), а не поле события. Из формы создания уведомление убрано осознанно.

## Сценарий: создание события

**Что видит пользователь:** нажимает «+ Событие», заполняет форму — название, дата, время начала/конца, проект, «весь день».

**API:** `POST /api/workspaces/:workspaceId/events`

```json
{
  "title": "Встреча с командой продукта",
  "startAt": "2026-09-09T14:00:00.000Z",
  "endAt": "2026-09-09T14:30:00.000Z",
  "allDay": false,
  "projectId": "3fa85f64-5717-4562-b3fc-2c963f66afa6"
}
```

Сервер:

- Проверяет членство в воркспейсе.
- `title` — trim + не пустой (иначе 400).
- Если передан `projectId` — проверяет, что проект существует и в этом воркспейсе (иначе 400).
- Проверяет `endAt >= startAt` (иначе 400).
- `allDay` по умолчанию `false`.

**Ответ:** `EventEntity` (201).

## Сценарий: список событий за период (Month-вью)

**Что видит пользователь:** открывает календарь на сентябрь — видит все события месяца, при необходимости отфильтрованные по проекту.

**API:** `GET /api/workspaces/:workspaceId/events?from=&to=&projectId=`

Query (все опционально):

- `from`, `to` — границы диапазона (ISO 8601). Возвращаются события, которые **пересекают** `[from, to]`, то есть `startAt <= to AND endAt >= from`. Так многодневное событие попадает в месяц, даже если началось раньше его начала.
- `projectId` — фильтр по проекту.
- Если `from > to` → 400.

Порядок: по `startAt` ascending.

**Ответ:** массив `EventEntity`.

## Сценарий: обновление события

**API:** `PATCH /api/events/:id` — частичное обновление, любые поля из `{ title?, startAt?, endAt?, allDay?, projectId? }`.

- Диапазон валидируется по **итоговым** значениям: если прислать только `endAt`, он сверяется с уже сохранённым `startAt` (иначе 400).
- `projectId: null` — открепить событие от проекта.
- Новый `projectId` проверяется на принадлежность воркспейсу (400).

**Ответ:** обновлённый `EventEntity`.

## Сценарий: отметить выполненным или снять отметку

**Что видит пользователь:** в списке задач дня ставит или снимает чекбокс у события.

**API:** `PATCH /api/events/:id/completion`

```json
{ "isCompleted": true }
```

`false` снимает отметку. `isCompleted` — JSON-boolean: нет поля, `null` или строка `"true"` → 422 (глобальный `ValidationPipe`). Новые события создаются с `isCompleted: false`. Поле приходит в `EventEntity` у списка, создания и обновления, чтобы чекбокс на фронте знал текущее состояние.

**Ответ:** обновлённый `EventEntity`. Событие не найдено → 404.

## Сценарий: удаление события

**API:** `DELETE /api/events/:id` → 204. Событие не найдено → 404.

## Ошибки

| Ситуация | Код |
|----------|-----|
| Не аутентифицирован | 401 |
| Не член воркспейса | 403 |
| Пустой `title` | 400 |
| `projectId` не существует или из другого воркспейса | 400 |
| `endAt` раньше `startAt` | 400 |
| `from` позже `to` (список) | 400 |
| Событие / воркспейс не найдены | 404 |
| Нет `isCompleted`, `null` или строка `"true"` (нужен JSON-boolean) | 422 |
