# Заметки и нюансы

Моменты, которые всплыли при описании сценариев, и их стоит держать в уме:

1. **Разные модели удаления.** Проекты удаляются жёстко, страницы — мягко (soft-delete через `deletedAt`). Пользователь должен это чувствовать в UI: у проектов нет «восстановить», у страниц — есть.

2. **Cascade на проектах рекурсивный.** Удалил родительский проект — потерял всё дерево подпроектов + все их страницы. Это агрессивно, но соответствует текущей схеме (`onDelete: Cascade` на `parentProjectId` и `projectId`).

3. **Перемещение страницы в другой проект — это смена projectId.** А вот «отвязка» страницы от проекта (projectId = null) — это не то, что происходит при удалении проекта: при удалении проекта страницы каскадно удаляются. projectId = null может случиться только при явном перемещении страницы «в корень воркспейса» (если такая фича будет).

4. **Права.** Управление воркспейсом (переименование, удаление, члены) — только owner (`assertOwner`). CRUD проектов — любой член (`assertMemberOf`). Для страниц планируется `assertMemberOf`.

5. **Проверка родителя.** При создании, перемещении и reorder проектов сервер проверяет, что `parentProjectId` существует и принадлежит тому же воркспейсу (иначе 400). Защита от циклов при перемещении (A → B → A) НЕ реализована (осознанно).

6. **Смена позиции.** Клиент не управляет `position` напрямую — только через bulk reorder (`PATCH /workspaces/:workspaceId/projects/order`), где `orderedIds` должен быть точной перестановкой всех соседей родителя. Механизм одинаковый для страниц — переиспользуем, когда дойдём.

7. **Каскады страниц.** `parentPageId` → `onDelete: SetNull` (при удалении родителя дети становятся корневыми), `projectId` → `onDelete: Cascade` (при удалении проекта страницы удаляются), `authorId` → `onDelete: Restrict`.

8. **Статус реализации.** Workspaces и Projects реализованы полностью. Pages: таблицы в схеме есть, эндпоинтов пока нет.
