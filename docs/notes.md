# Заметки и нюансы

Моменты, которые всплыли при описании сценариев, и их стоит держать в уме:

1. **Разные модели удаления.** Проекты удаляются жёстко, страницы — мягко (soft-delete через `deletedAt`). Пользователь должен это чувствовать в UI: у проектов нет «восстановить», у страниц — есть.

2. **Cascade на проектах рекурсивный.** Удалил родительский проект — потерял всё дерево подпроектов + все их страницы. Это агрессивно, но соответствует текущей схеме (`onDelete: Cascade` на `parentProjectId` и `projectId`).

3. **Перемещение страницы в другой проект — это смена projectId.** А вот «отвязка» страницы от проекта (projectId = null) — это не то, что происходит при удалении проекта: при удалении проекта страницы каскадно удаляются. projectId = null может случиться только при явном перемещении страницы «в корень воркспейса» (если такая фича будет).

4. **Права.** Управление воркспейсом (переименование, удаление, члены) — только owner (`assertOwner`). CRUD проектов — любой член (`assertMemberOf`). Для страниц планируется `assertMemberOf`.

5. **Проверка родителя.** При создании, перемещении и reorder проектов сервер проверяет, что `parentProjectId` существует и принадлежит тому же воркспейсу (иначе 400). Это дублируется на уровне БД композитным ключом `(parentProjectId, workspaceId) → (id, workspaceId)` — обойти проверку кода не выйдет. Защита от циклов при перемещении (A → B → A) НЕ реализована (осознанно).

6. **Смена позиции.** Клиент не управляет `position` напрямую — только через bulk reorder (`PATCH /workspaces/:workspaceId/projects/order`), где `orderedIds` должен быть точной перестановкой всех соседей родителя. Переупорядочивание выполняется двухфазно (сдвиг на оффсет → финальные индексы), потому что на позициях стоит уникальный индекс `NULLS NOT DISTINCT`. Механизм одинаковый для страниц — переиспользуем, когда дойдём.

7. **Страницы без вложенности.** Вложенность создаёт только проект (папка) — «страница в странице» не поддерживается. Поле `parentPageId` осталось в схеме исторически и **будет убрано в будущей задаче** (вместе с `pages_parentPageId_workspaceId_fkey` и упрощением индекса позиций). Сейчас: `projectId` → `onDelete: Cascade` (при удалении проекта страницы удаляются), `authorId` → `onDelete: Restrict`.

8. **Целостность на уровне БД.** `@@unique([id, workspaceId])` на Project/Page; composite FK на родителя/проект гарантируют «тот же воркспейс»; частичный индекс `one_owner_per_workspace` гарантирует одного OWNER; уникальные позиции — `NULLS NOT DISTINCT` (raw-SQL, миграция в проде ещё не применена). Prisma-ошибки P2002/P2003/P2025 глобально превращаются в 409/400/404 через `PrismaExceptionFilter`.

9. **Статус реализации.** Workspaces и Projects реализованы полностью. Pages: таблицы в схеме есть, эндпоинтов пока нет. Миграция БД (`add_integrity_constraints`) не применена — ждёт починки доступа (P1000).
