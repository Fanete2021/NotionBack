# Pages

> Примечание: таблицы Page и PageContent уже есть в схеме БД, но эндпоинты для страниц пока **не реализованы**. Сценарии ниже — целевое поведение.

## Сценарий 6. Создание страницы внутри проекта

**Что видит пользователь:** Наводит на проект «Диплом», нажимает «+». В контекстном меню выбирает «Создать страницу» (в отличие от «Создать проект»). Либо внутри проекта уже есть страницы, и кнопка «+» создаёт страницу по умолчанию.

**Что делает:** Вводит название страницы, например «Введение».

**Что происходит внутри:** `POST /api/pages` (тело: `{ title, workspaceId, projectId: "uuid-диплома", type: "DOC" }`). Сервер:

- Проверяет членство в воркспейсе.
- Создаёт Page с projectId = "uuid-диплома", parentPageId = null, authorId = userId.
- Создаёт пустую запись PageContent (пустой JSON для редактора).
- Возвращает метаданные страницы (response-DTO без контента).

**Результат:** В сайдбаре внутри «Диплом» появляется страница «Введение» (с иконкой 📄). При клике на неё открывается область редактора — пустая страница с заголовком «Введение» и курсором для ввода контента.

```
ПРОЕКТЫ
  ● Диплом                     ← проект
      📄 Введение              ← страница (projectId = Диплом)
      ▸ Глава 1               ← подпроект
```

**Ошибки:**

- Пользователь не член воркспейса → 403.
- Проект не найден → 404.
- Пустой заголовок → 400.

## Сценарий 7. Создание страницы внутри страницы (вложенные страницы)

**Что видит пользователь:** Наводит на существующую страницу «Введение», нажимает «+» или контекстное меню. Выбирает «Создать подстраницу».

**Что делает:** Вводит название, например «Постановка задачи».

**Что происходит внутри:** `POST /api/pages` (тело: `{ title, workspaceId, projectId: "uuid-диплома", parentPageId: "uuid-введения" }`). Сервер:

- Проверяет членство.
- Проверяет, что parentPageId принадлежит этому же воркспейсу.
- Создаёт страницу с parentPageId = "uuid-введения".
- Создаёт PageContent.

**Результат:** «Введение» раскрывается, внутри видна «Постановка задачи».

```
  ● Диплом
      ▸ Введение              ← страница-родитель
          📄 Постановка задачи  ← дочерняя страница
      ▸ Глава 1
```

**Важно про каскады:** У parentPageId стоит onDelete: SetNull — если удалить «Введение», то «Постановка задачи» не удалится, а станет корневой страницей (её parentPageId станет null). Это отличается от проектов, где каскад жёсткий.

## Сценарий 10. Перемещение страницы из одного места в другое

**Что видит пользователь:** Drag-n-drop страницы «Компоненты» из проекта «Дизайн-система» в проект «Дорожная карта». Либо через контекстное меню → «Переместить».

**Что происходит внутри:** `PATCH /api/pages/:id` с обновлением projectId и/или parentPageId. Сервер:

- Проверяет членство в воркспейсе.
- Если новый projectId — проверяет, что целевой проект в том же воркспейсе.
- Если новый parentPageId — проверяет, что целевая страница в том же воркспейсе (и это не потомок текущей — защита от циклов).
- Обновляет поля.

**Результат:** Страница «Компоненты» теперь внутри «Дорожная карта».

```
Было:                              Стало:
  ▸ Продукт                          ▸ Продукт
      ▸ Дизайн-система                  ▸ Дизайн-система
          📄 Компоненты  ←── moved        ▸ Дорожная карта
      ▸ Дорожная карта                       📄 Компоненты
```

Крайний случай — удаление родительской страницы: В отличие от проектов, здесь onDelete: SetNull. Если удалить родительскую страницу, дочерние страницы не удалятся, а станут корневыми (parentPageId = null).

## Сценарий 13. Удаление страницы

**Что видит пользователь:** В сайдбаре контекстное меню на странице «Отчёт Q4» → «Удалить». Либо внутри редактора — кнопка «...» → «Удалить». Страница не удаляется окончательно, а перемещается в корзину.

**Что делает:** Подтверждает удаление.

**Что происходит внутри:** `DELETE /api/pages/:id`. Сервер:

- `assertMemberOf` — проверка членства.
- Soft-delete: устанавливает deletedAt = now() на странице и на всех её потомках (рекурсивно по parentPageId).
- Страницы не удаляются из БД — они просто получают deletedAt.
- В обычных запросах (где deletedAt IS NULL) эти страницы не видны. В `GET /api/trash` — видны.

**Результат:** Страница «Отчёт Q4» исчезает из дерева в сайдбаре и из обычных списков. Появляется в 🗑 Корзине. При клике на Корзину пользователь видит все удалённые страницы с датой удаления.

- Восстановление: `POST /api/pages/:id/restore` — сбрасывает deletedAt у страницы и всех её потомков. Страница возвращается на прежнее место в дереве.
- Окончательное удаление: `DELETE /api/pages/:id/hard` — удаляет страницу из БД навсегда (с контентом). Используется из корзины.

```
Было:                            Стало (в сайдбаре):
  ▸ Диплом                         ▸ Диплом
      📄 Введение                      📄 Введение
      📄 Отчёт Q4  ←── в корзину      📄 Черновик

Корзина:
  📄 Отчёт Q4  (удалён 2 часа назад)
```

Крайний случай — удаление страницы, у которой есть дочерние страницы: Все потомки тоже получают deletedAt (рекурсивный soft-delete). В корзине они видны как отдельные элементы.

Крайний случай — удаление проекта со страницами (из сценария 12): Страницы удаляются жёстко (Cascade), минуя корзину. Корзина работает только при прямом удалении отдельной страницы.
