# Pages

> Примечание: таблицы Page и PageContent уже есть в схеме БД, но эндпоинты для страниц пока **не реализованы**. Сценарии ниже — целевое поведение.
>
> **Вложенности «страница в странице» нет.** Иерархию создают проекты (папки): страницы лежат плоским списком внутри проекта и упорядочены по `position`. Поле `parentPageId` в схеме осталось исторически и **будет убрано в одной из будущих задач** — в сценариях ниже оно не используется.

## Сценарий 6. Создание страницы внутри проекта

**Что видит пользователь:** Наводит на проект «Диплом», нажимает «+». В контекстном меню выбирает «Создать страницу» (в отличие от «Создать проект»). Либо внутри проекта уже есть страницы, и кнопка «+» создаёт страницу по умолчанию.

**Что делает:** Вводит название страницы, например «Введение».

**Что происходит внутри:** `POST /api/pages` (тело: `{ title, workspaceId, projectId: "uuid-диплома", type: "DOC" }`). Сервер:

- Проверяет членство в воркспейсе.
- Создаёт Page с projectId = "uuid-диплома" и authorId = userId; страница попадает в конец списка страниц проекта (position = количество страниц в проекте).
- Создаёт пустую запись PageContent (пустой JSON для редактора).
- Возвращает метаданные страницы (response-DTO без контента).

**Результат:** В сайдбаре внутри «Диплом» появляется страница «Введение» (с иконкой 📄). При клике на неё открывается область редактора — пустая страница с заголовком «Введение» и курсором для ввода контента.

```
ПРОЕКТЫ
  ● Диплом                     ← проект
      📄 Введение              ← страница (projectId = Диплом)
      ▸ Глава 1               ← подпроект
```

**Ошибки:**

- Пользователь не член воркспейса → 403.
- Проект не найден → 404.
- Пустой заголовок → 400.

## Сценарий 7. Несколько страниц в одном проекте

**Что видит пользователь:** Внутри проекта «Диплом» уже есть страницы «Введение» и «Черновик». Нажимает «+» внутри проекта — появляется новая страница в списке.

**Что делает:** Вводит название, например «Постановка задачи».

**Что происходит внутри:** `POST /api/pages` (тело: `{ title, workspaceId, projectId: "uuid-диплома" }`). Сервер:

- Проверяет членство в воркспейсе.
- Проверяет, что projectId принадлежит этому же воркспейсу.
- Создаёт страницу внутри проекта; позиция — конец списка (position = количество страниц в проекте).
- Создаёт PageContent.

**Результат:** В проекте «Диплом» появляется ещё одна страница. Порядок страниц внутри проекта — по `position` (переупорядочивание — как у проектов, через bulk reorder).

```
  ● Диплом
      📄 Введение            ← страница (projectId = Диплом)
      📄 Постановка задачи   ← ещё одна страница
      ▸ Глава 1             ← подпроект
```

**Важно:** Страницы не вкладываются друг в друга — вложенность создаёт только проект (папка). Удаление одной страницы не влияет на другие (нет «родитель-потомок»).

### Ограничения целостности на уровне БД

- **Композитный ключ целостности**: у страницы есть `@@unique([id, workspaceId])`, а `projectId` ссылается по паре `(projectId, workspaceId) → (id, workspaceId)`. БД сама гарантирует, что целевой проект существует и **принадлежит тому же воркспейсу**.
- **Уникальность позиций среди соседей**: индекс `pages_position_unique` на `(workspace_id, project_id, parent_page_id, position)` с `NULLS NOT DISTINCT`. Когда `parentPageId` уберут из схемы (будущая задача), индекс упростится до `(workspace_id, project_id, position)`.

## Сценарий 10. Перемещение страницы из одного места в другое

**Что видит пользователь:** Drag-n-drop страницы «Компоненты» из проекта «Дизайн-система» в проект «Дорожная карта». Либо через контекстное меню → «Переместить».

**Что происходит внутри:** `PATCH /api/pages/:id` с обновлением `projectId`. Сервер:

- Проверяет членство в воркспейсе.
- Проверяет, что целевой проект в том же воркспейсе.
- Обновляет `projectId`; страница попадает в конец списка страниц нового проекта.

**Результат:** Страница «Компоненты» теперь внутри «Дорожная карта».

```
Было:                              Стало:
  ▸ Продукт                          ▸ Продукт
      ▸ Дизайн-система                  ▸ Дизайн-система
          📄 Компоненты  ←── moved        ▸ Дорожная карта
      ▸ Дорожная карта                       📄 Компоненты
```

Крайний случай — перемещение в корень воркспейса: если такая возможность понадобится (projectId = null), добавим отдельно. На текущий момент страница всегда принадлежит какому-то проекту.

## Сценарий 13. Удаление страницы

**Что видит пользователь:** В сайдбаре контекстное меню на странице «Отчёт Q4» → «Удалить». Либо внутри редактора — кнопка «...» → «Удалить». Страница не удаляется окончательно, а перемещается в корзину.

**Что делает:** Подтверждает удаление.

**Что происходит внутри:** `DELETE /api/pages/:id`. Сервер:

- `assertMemberOf` — проверка членства.
- Soft-delete: устанавливает deletedAt = now() на самой странице.
- Страница не удаляется из БД — она просто получает deletedAt.
- В обычных запросах (где deletedAt IS NULL) эта страница не видна. В `GET /api/trash` — видна.

**Результат:** Страница «Отчёт Q4» исчезает из дерева в сайдбаре и из обычных списков. Появляется в 🗑 Корзине. При клике на Корзину пользователь видит все удалённые страницы с датой удаления.

- Восстановление: `POST /api/pages/:id/restore` — сбрасывает deletedAt у страницы. Страница возвращается на прежнее место в списке.
- Окончательное удаление: `DELETE /api/pages/:id/hard` — удаляет страницу из БД навсегда (с контентом). Используется из корзины.

```
Было:                            Стало (в сайдбаре):
  ▸ Диплом                         ▸ Диплом
      📄 Введение                      📄 Введение
      📄 Отчёт Q4  ←── в корзину      📄 Черновик

Корзина:
  📄 Отчёт Q4  (удалён 2 часа назад)
```

Крайний случай — удаление страницы, у которой есть дочерние страницы: страницы не имеют вложенности, поэтому удаление одной страницы не затрагивает другие.

Крайний случай — удаление проекта со страницами (из сценария 12): Страницы удаляются жёстко (Cascade), минуя корзину. Корзина работает только при прямом удалении отдельной страницы.
