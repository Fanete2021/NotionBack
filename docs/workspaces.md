# Workspaces

## Сценарий 1.5. Открытие рабочего пространства

**Что видит пользователь:** После логина/регистрации открывается главный экран. Левый сайдбар (~260px), основная область справа.

Сайдбар сверху вниз:

- Название воркспейса — например «Рабочее пространство» — с иконкой (кружок) и кнопкой редактирования (карандаш) справа.
- Поиск — поле «Поиск страниц...» с подсказкой горячей клавиши ⌘K.
- Быстрые ссылки: 🏠 Главная, 📄 Документы.
- Секция «ПРОЕКТЫ» — заголовок капслоком, справа кнопки «+» (создать проект) и «...» (меню действий).
- Дерево проектов — иерархический список. Каждый проект может содержать дочерние проекты и страницы. Текущий активный элемент подсвечен фоном. У проектов могут быть цветные маркеры (●) и иконки.
- Разделитель.
- Системные ссылки: 📅 Календарь, 🗑 Корзина, ⚙ Настройки.
- Профиль в самом низу — аватар (инициалы), имя, email, кнопка «...» (меню профиля/выход).

Основная область: Если выбран конкретный проект или страница — открывается соответствующий контент. Если ничего не выбрано — возможно, пустая область или «Главная».

**Что происходит внутри:** При загрузке приложения фронтенд запрашивает список воркспейсов пользователя (через `GET /api/auth/me` или отдельный эндпоинт) и дерево проектов текущего воркспейса: `GET /api/workspaces/:workspaceId/projects` — возвращает дерево с childProjects вложенными.

**Важно для этой задачи:** Страницы (📄 элементы в дереве) пока не имеют эндпоинтов — в сайдбаре они не отображаются или отображаются статично. Реальный фокус — на воркспейсах и проектах.

## Сценарий 2. Создание своего воркспейса

**Что видит пользователь:** Находясь в любом месте приложения, пользователь открывает меню (например, кнопку «...» в профиле или переключатель воркспейса) и выбирает «Создать рабочее пространство». Появляется форма/modal с единственным полем — «Название».

**Что делает:** Вводит название, например «Side Project». Нажимает «Создать».

**Что происходит внутри:** `POST /api/workspaces` (тело: `{ name }`). Сервер:

- Берёт userId из JWT.
- Создаёт Workspace с name = "Side Project", ownerId = userId.
- Создаёт WorkspaceMember с role = OWNER.
- Возвращает созданный воркспейс (response-DTO без служебных полей).

**Результат:** Новый воркспейс появляется в списке. Пользователь автоматически переключается в него (фронтенд обновляет текущий workspaceId). Сайдбар теперь показывает пустой workspace — секция «ПРОЕКТЫ» пуста, нет ни одного проекта.

**Ошибки:**

- Пустое название → 400 (валидация DTO, `@IsNotEmpty()`).
- Неавторизован → 401 (JwtAuthGuard).

## Сценарий 3. Обновление данных существующего воркспейса

**Что видит пользователь:** В сайдбаре рядом с названием воркспейса «Рабочее пространство» — иконка карандаша ✏️. Нажимает на неё. Название становится редактируемым (inline-редактирование) или открывается small modal.

**Что делает:** Меняет название, например на «Мой личный space». Нажимает Enter или кнопку сохранения.

**Что происходит внутри:** `PATCH /api/workspaces/:id` (тело: `{ name }`). Сервер проверяет через `assertOwner(userId, workspaceId)` — только owner может переименовывать воркспейс. Обновляет name в БД.

**Результат:** Название в сайдбаре мгновенно обновляется. Обратите внимание: у Workspace в схеме нет `updatedAt` — это поле не отслеживается.

**Ошибки:**

- Пользователь не owner воркспейса → 403 (assertOwner).
- Воркспейс не найден → 404.
- Пустое название → 400.

**Отличие от проектов:** Для проектов достаточно быть любым членом воркспейса (assertMemberOf). Для управления воркспейсом — именно owner.

## Сценарий 11. Удаление воркспейса

**Что видит пользователь:** В настройках воркспейса или через меню «...» → «Удалить рабочее пространство». Появляется подтверждение: «Вы уверены? Все проекты и страницы будут удалены безвозвратно».

**Что делает:** Подтверждает удаление.

**Что происходит внутри:** `DELETE /api/workspaces/:id`. Сервер:

- `assertOwner(userId, workspaceId)` — только owner может удалить воркспейс.
- Удаляет Workspace. Cascade удаляет всё:
  - Все WorkspaceMember (каскад).
  - Все Project (каскад) → все дочерние проекты (каскад по parentProjectId).
  - Все Project → все Page внутри этих проектов (каскад по projectId).
  - Все Page → все PageContent (каскад).
  - Страницы без проекта (projectId = null) тоже удаляются, потому что cascade идёт от workspaceId на страницах.

**Результат:** Воркспейс исчезает. Если это был единственный воркспейс пользователя — фронтенд должен предложить создать новый или перенаправить на страницу создания.

**Ошибки:**

- Пользователь не owner → 403.
- Воркспейс не найден → 404.

**Крайний случай — authorId Restrict:** Если у какой-то страницы authorId указывает на пользователя, который был удалён — это невозможно, потому что authorId имеет `onDelete: Restrict`. Но при удалении воркспейса пользователи не удаляются — удаляются только связи через WorkspaceMember.
